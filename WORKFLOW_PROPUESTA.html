FamSPI — Workspace Unificado de Compras

Plan de implementación: Backend + DB, Frontend, Checklist de cambios

Diagnóstico y propuesta — Workspace unificado

El ciclo de compras está hoy fragmentado en 11 rutas y workspaces. Un mismo expediente cambia de pantalla según el rol, rompiendo la trazabilidad. La state machine ya es sólida en backend; la fragmentación es puramente de navegación y UI.

Estado actual vs. propuesto

Hoy: 11 workspaces fragmentados

  • /comercial/equipment-purchases — compra pública
  • /purchases/workspace — listado mixto
  • /backoffice/private-purchases — 3 000 líneas
  • /logistica/private-purchases — mismos datos, otra pantalla
  • /servicio-tecnico/entregas-privadas — post-arrival
  • /servicio-tecnico/workspace-procedimiento — F.ST-07/F.ST-20
  • /comercial/delivery-ceilings — cupos públicos
  • /gerencia/compras-album — álbum gerencia
  • /servicio-tecnico/aplicaciones — entrenamiento
  • /servicio-tecnico/asistencia — asistencia
  • /servicio-tecnico/desinfeccion — F.ST-02

Propuesto: 1 workspace, 6 sub-tabs

  • /dashboard/compras — ruta única
  • Sub-tab 1: Comercial — oferta, BC, SOCE
  • Sub-tab 2: Contrato — docs, firmas, gate
  • Sub-tab 3: Logística — despacho, F.ST-14
  • Sub-tab 4: Técnica — F.ST-07, F.ST-09, CU, F.ST-10
  • Sub-tab 5: Entrenamiento — F.ST-04, F.ST-05, cert.
  • Sub-tab 6: Timeline — auditoría, bloqueos
  • Adyacentes independientes siguen en navbar propio (retiros, preventivo, correctivo)

Principios de diseño del workspace

Todos los roles ven todo el expediente

La visibilidad no se restringe por rol. Las acciones se gatean por rol dentro de cada sub-tab. El comercial puede ver la sub-tab Técnica aunque no pueda actuar en ella.

Sub-tabs con badge de estado

Cada sub-tab muestra un badge: pendiente en curso bloqueado completado n/a. De un vistazo se conoce el estado de todo el expediente.

Compra pública y privada, misma estructura

El workspace es agnóstico al tipo. La sub-tab Comercial muestra la sección SOCE para compras públicas y la sección Business Case para comodato. El resto de sub-tabs es idéntico.

Post-arrival unificado para ambos tipos

Hoy F.ST-14/F.ST-09/F.ST-10/entrenamiento solo existen en UI para compra privada. Se extiende installationWorkflow para que la compra pública también use el mismo flujo.

Plan Backend y Base de Datos

Los cambios de backend son acotados: la state machine privada y el STATUS público quedan intactos. Los trabajos principales son: nuevos campos SERCOP, extender installationWorkflow a compra pública, y consolidar endpoints para el workspace unificado.

Regla de oro: No se toca la state machine de compra privada ni el STATUS dictionary de compra pública. Solo se agregan campos, se extiende installationWorkflow, y se crean/ajustan endpoints que el frontend necesita para el workspace unificado.

Plan Frontend — Workspace Unificado

Arquitectura de componentes, estructura de archivos, y reglas de diseño derivadas de DESIGN.md. El workspace usa lista lateral + panel de detalle con 6 sub-tabs. Todos los componentes respetan el Design System naval.

Escena de uso: Asesor comercial revisando el estado de un expediente de comodato en desktop de oficina, backoffice aprobando un contrato, jefe técnico asignando instalador desde tablet. La interfaz debe ser densa pero legible, con estado y bloqueos visibles sin scroll.

Layout del workspace

El workspace usa una distribución de dos paneles: lista lateral fija (320px) y panel de detalle expandido. En tablet colapsado el panel lista se oculta con un botón de retroceso. En mobile es un listado que navega a la pantalla completa de detalle.

// PurchasesWorkspacePage.jsx — layout raíz <div className="flex min-w-0 h-[calc(100vh-64px)]"> <PurchaseListPanel {/* 320px, sticky, overflow-y-auto */} onSelect={setSelectedId} selectedId={selectedId} /> <PurchaseDetailPanel {/* flex-1, overflow-y-auto */} purchaseId={selectedId} /> </div>

Componentes clave: especificaciones de diseño

A

PurchaseListItem — estado, tipo y bloqueo visible

  • Altura fija 72px — nunca variable para mantener scroll predecible.
  • Left: badge de tipo (pública / comodato / directa) + nombre del cliente en 14px/600.
  • Right: badge de estado principal + si hay bloqueo activo, un dot rojo 8px sobre el badge.
  • Seleccionado: fondo #EFF6FF, borde izquierdo NO (baneado por DESIGN.md); usar fondo tintado completo.
  • cursor-pointer + scale(0.99) en :active.
B

PurchaseTabNav — 6 tabs con badge de estado

  • Tab activo: texto Ink Slate 14px/600, indicador inferior 2px solid Action Blue — sin gradiente.
  • Tab inactivo: texto Warm Ash, sin indicador.
  • Cada tab lleva un TabStatusBadge alineado a la derecha del label: colores semánticos (amber=pendiente, blue=en curso, red=bloqueado, green=completado, gray=n/a).
  • Transición de tab: 150ms ease-out. Solo cambia el contenido, no anima el tab en sí (se usa decenas de veces al día — DESIGN.md, animation rules).
C

ActionGate — acciones gateadas por rol

Wrapper que renderiza sus children solo si el usuario tiene el rol requerido. Si no tiene rol, renderiza nada (no un botón deshabilitado, no un tooltip de permisos — simplemente no aparece).

// Uso en cualquier sub-tab <ActionGate roles={['jefe_comercial', 'gerencia_general']}> <Button onClick={handleApprove}>Aprobar contrato</Button> </ActionGate>
D

SoceTrackSection — pista SOCE (solo compra pública)

  • Visible solo si purchase.type === 'public'.
  • Muestra los campos SERCOP nuevos en una cuadrícula de lectura (tipo formulario read-only con labels en 12px/500).
  • Si outcome === 'won': muestra badge verde GANADO + campos de adjudicación.
  • Si outcome === 'lost': muestra badge rojo NO ADJUDICADO + motivo.
  • Formulario de edición inline (no modal) para registrar resultado de puja, número de resolución, OC.
E

DocumentGateChecklist — gate de 9 documentos

  • Lista vertical con 9 ítems. Cada ítem: ícono de check verde si está completo, círculo gris si falta.
  • No usar cards por cada ítem — es una lista simple con íconos semánticos.
  • Al pie: contador N de 9 documentos completos en 12px/Warm Ash.
  • Botón "Enviar a gerencia" deshabilitado hasta que los 9 estén completos.
F

BlockerAlert — bloqueos activos

Si hay bloqueos activos en computeInstallationClosureGate, mostrar un banner no-modal en la parte superior del panel de detalle. Fondo var(--red-lt), texto descriptivo del bloqueo, sin modal.

// BlockerAlert.jsx if (!blockers.length) return null; return ( <div className="bg-red-50 border border-red-200 rounded-xl p-4 flex gap-3"> {/* ícono de alerta + lista de bloqueos activos */} </div> );
